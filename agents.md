# Agents Guide

This file is for coding agents and automated collaborators working inside the Chiron monorepo. Use it as the default operating context before making changes.

## Mission

Chiron is a Turborepo-based monorepo with:

- `apps/web`: Next.js 15 + TypeScript frontend
- `backend`: FastAPI API + Python agent worker runtime
- `packages/contracts`: generated TypeScript API contract surface derived from backend OpenAPI
- `packages/ui`: shared React UI primitives

The repo is designed for:

- independent deployment of web, API, and workers
- typed frontend/backend integration through generated contracts
- realtime agent visibility via REST + WebSocket
- production-oriented observability and scaling boundaries

## Architectural Rules

1. Python models are the source of truth for API contracts.
2. The frontend should import types from `@chiron/contracts`, not from backend code or ad hoc local duplicates.
3. Do not hand-edit `packages/contracts/src/generated/api.ts`. Regenerate it.
4. If you change API request or response models, regenerate OpenAPI/contracts and verify the frontend still typechecks.
5. Keep API and worker concerns separated. Shared logic belongs in `backend/src/chiron_backend/common` or a future dedicated backend shared package.
6. Prefer adding new REST routes under `backend/src/chiron_backend/api/routes/` and keep websocket behavior centralized in `api/main.py` unless there is a clear routing abstraction worth introducing.
7. Treat the current `RealtimeHub` as a local-development adapter. Production-grade pub/sub should preserve its interface shape where possible.

## Working Agreements

- Make the smallest correct change that preserves the existing architecture.
- Avoid broad refactors unless they are necessary for correctness or explicitly requested.
- Preserve the monorepo boundaries. Do not collapse frontend/backend/shared responsibilities together.
- Keep generated assets generated.
- Prefer root scripts over ad hoc commands because Turbo encodes the intended build graph.

## Environment Assumptions

- Node dependencies live in the workspace via `pnpm`.
- Python dependencies are expected in the repo root virtualenv at `./.venv`.
- Backend package scripts intentionally use `../.venv/bin/python` so root Turbo runs work consistently.

If you add new Python tooling, wire it through the repo venv and keep backend scripts compatible with that setup.

## Standard Commands

Run these from the repo root unless there is a specific reason not to.

### Setup

```bash
pnpm install
python3 -m venv .venv
./.venv/bin/pip install -r backend/requirements-dev.txt
```

### Development

```bash
pnpm dev
```

### Verification

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
docker compose config -q
```

### Formatting

```bash
pnpm format
```

## Language and Tooling Conventions

### TypeScript / Next.js

- Shared TS lint config lives in `eslint.config.mjs`.
- Formatting uses Prettier with the root `.prettierignore`.
- `apps/web/next.config.mjs` uses `typedRoutes` and standalone output.
- `next build` skips linting because lint is already enforced separately at repo level.
- Keep imports against workspace packages stable:
  - `@chiron/contracts`
  - `@chiron/ui`

### Python / FastAPI

- Formatting and linting use Ruff.
- Typechecking uses mypy in strict mode.
- Shared settings live in `common/config.py`.
- Shared Pydantic models live in `common/models.py`.
- If you add app state dependencies, initialize them in lifespan and provide a safe fallback when tests or local flows can instantiate the app differently.

## Contract Workflow

When backend API models or routes change:

1. Update Python models/routes.
2. Regenerate OpenAPI:

```bash
pnpm contracts:generate
```

3. Confirm `packages/contracts/src/index.ts` still exports the stable shapes the frontend expects.
4. Run:

```bash
pnpm typecheck
pnpm build
```

Important:

- `packages/contracts/src/generated/api.ts` reflects OpenAPI generator output, not ergonomic frontend aliases.
- `packages/contracts/src/index.ts` is the right place to define stable exported aliases/interfaces on top of generated schema types.

## Testing Expectations

Before handing off meaningful code changes, run the narrowest relevant checks and then the root checks when the change crosses boundaries.

Typical minimums:

- frontend-only change: `pnpm lint`, `pnpm typecheck`, `pnpm build`
- backend-only change: `pnpm lint`, `pnpm typecheck`, `pnpm test`
- contract or cross-stack change: all root verification commands

Add tests when behavior changes:

- `backend/tests/unit`: pure logic or model behavior
- `backend/tests/integration`: API route behavior, app state, request/response flows

## Common Pitfalls

- Editing generated contract files directly
- Forgetting to regenerate contracts after backend schema changes
- Running backend tools against system Python instead of `./.venv`
- Introducing frontend types that drift from backend models
- Relying on app state that exists in production boot but not in tests
- Formatting package directories without the root `.prettierignore`

## Preferred Change Patterns

### Adding a new backend endpoint

1. Add or extend Pydantic models in `common/models.py` or a focused module if the model set grows.
2. Add route logic under `api/routes/`.
3. Register the router if needed.
4. Add or update tests.
5. Regenerate contracts.
6. Update frontend API client usage through `@chiron/contracts`.

### Adding realtime UI

1. Add backend event payload shape intentionally.
2. Expose the event over the websocket boundary.
3. Export or adapt the corresponding frontend type in `packages/contracts/src/index.ts`.
4. Consume it in `apps/web/src/lib/realtime` or the relevant component.

### Adding shared UI

1. Put reusable primitives in `packages/ui`.
2. Keep app-specific composition in `apps/web`.
3. Avoid leaking backend/domain logic into the UI package.

## When to Pause

Stop and ask for clarification if:

- a requested change conflicts with the frontend/backend contract model
- a refactor would move generated files into source-of-truth status
- a production decision is required on Redis/Postgres/queue topology beyond the current scaffold
- a change would require destructive cleanup of user work
